# Kafka - Outbox, Topics and Consumers

For `transport: kafka`. Events leave the write side through a transactional outbox and reach the read side through a consumer that is idempotent and has a dead-letter topic.

Kafka is the transport, not the event store. The write database is the source of truth; a topic keeps its events only so that a projection can be rebuilt by replaying them.

## Transactional Outbox

Never send to Kafka inside the business transaction. If the send succeeds and the transaction rolls back, the read side sees a change that never happened; if the transaction commits and the send fails, the change is never seen. The command handler writes the event into an outbox table in its own transaction instead, and a relay publishes it afterwards.

```sql
-- V2__create_outbox_event.sql
CREATE TABLE outbox_event (
    id           BIGINT GENERATED BY DEFAULT AS IDENTITY,
    topic        VARCHAR(100) NOT NULL,
    aggregate_id VARCHAR(100) NOT NULL,
    event_type   VARCHAR(100) NOT NULL,
    payload      TEXT         NOT NULL,
    created_at   TIMESTAMP WITH TIME ZONE NOT NULL,
    published_at TIMESTAMP WITH TIME ZONE,
    CONSTRAINT pk_outbox_event PRIMARY KEY (id)
);

CREATE INDEX ix_outbox_event_unpublished ON outbox_event (id) WHERE published_at IS NULL;
```

```java
/** Stores an event in the outbox table, in the transaction of the command that produced it. */
@Component
public class Outbox {

    private final JdbcClient jdbc;
    private final JsonMapper jsonMapper;   // tools.jackson.databind.json.JsonMapper (Jackson 3)

    public Outbox(JdbcClient jdbc, JsonMapper jsonMapper) {
        this.jdbc = jdbc;
        this.jsonMapper = jsonMapper;
    }

    @Transactional(propagation = Propagation.MANDATORY)
    public void append(String topic, Object aggregateId, Object event) {
        jdbc.sql("""
                INSERT INTO outbox_event (topic, aggregate_id, event_type, payload, created_at)
                VALUES (:topic, :aggregateId, :eventType, :payload, now())
                """)
                .param("topic", topic)
                .param("aggregateId", String.valueOf(aggregateId))
                .param("eventType", event.getClass().getSimpleName())
                .param("payload", jsonMapper.writeValueAsString(event))
                .update();
    }
}
```

`Propagation.MANDATORY` makes a call outside a transaction fail instead of writing an event for a change that may not commit.

### Relay

```java
/** The only class that publishes to Kafka: sends unpublished outbox rows in order, then marks them. */
@Component
public class OutboxRelay {

    public static final String EVENT_TYPE_HEADER = "event-type";

    record Row(Long id, String topic, String aggregateId, String eventType, String payload) {
    }

    private final JdbcClient jdbc;
    private final KafkaTemplate<String, String> kafka;

    public OutboxRelay(JdbcClient jdbc, KafkaTemplate<String, String> kafka) {
        this.jdbc = jdbc;
        this.kafka = kafka;
    }

    @Scheduled(fixedDelayString = "${outbox.relay.delay:500ms}")
    @Transactional
    public void publish() throws Exception {
        // FOR UPDATE without SKIP LOCKED: a second replica waits, so events of one aggregate stay in order
        List<Row> rows = jdbc.sql("""
                SELECT id, topic, aggregate_id, event_type, payload FROM outbox_event
                WHERE published_at IS NULL ORDER BY id LIMIT 100 FOR UPDATE
                """).query(Row.class).list();
        for (Row row : rows) {
            ProducerRecord<String, String> record = new ProducerRecord<>(row.topic(), row.aggregateId(), row.payload());
            record.headers().add(EVENT_TYPE_HEADER, row.eventType().getBytes(StandardCharsets.UTF_8));
            kafka.send(record).get(10, TimeUnit.SECONDS);   // wait for the broker's acknowledgement
        }
        if (!rows.isEmpty()) {
            jdbc.sql("UPDATE outbox_event SET published_at = now() WHERE id IN (:ids)")
                    .param("ids", rows.stream().map(Row::id).toList())
                    .update();
        }
    }
}
```

- `@EnableScheduling` on the application class.
- The relay's transaction is its own, not a business transaction: it only reads and marks outbox rows.
- A row is marked only after the broker acknowledged it. When a send fails, the transaction rolls back and the whole batch is sent again, so an event can arrive twice and consumers must be idempotent.
- `FOR UPDATE` without `SKIP LOCKED` lets only one replica publish at a time. `SKIP LOCKED` would let a second replica overtake the first and deliver events of one aggregate out of order.
- Delete published rows on a schedule (for example older than seven days); the topic keeps the events.
- The payload is a JSON string and the event type travels in a header, so the producer and the consumer keep the default `String` serializers and need no type mapping or trusted packages.

## Producer and Topics

```yaml
spring:
  kafka:
    bootstrap-servers: ${SPRING_KAFKA_BOOTSTRAP_SERVERS:localhost:9092}
    producer:
      acks: all
      properties:
        enable.idempotence: true
```

```java
@Configuration
public class KafkaTopicConfig {

    /** One topic per aggregate type; no retention limit, so projections can be rebuilt by replaying it. */
    @Bean
    NewTopic orderEvents() {
        return TopicBuilder.name(OrderEvent.TOPIC).partitions(3).replicas(1)
                .config(TopicConfig.RETENTION_MS_CONFIG, "-1")
                .build();
    }
}
```

- **Key = aggregate id.** All events of one aggregate go to one partition and keep their order.
- **One topic per aggregate type,** named `<aggregate>-events`. The name is a constant on the aggregate's sealed event interface.
- **The command service owns the topic** and declares it. The replica count comes from configuration in a real cluster (three brokers, `replicas(3)`).
- **No retention limit** (`retention.ms=-1`) on domain event topics. Never raise the partition count of a topic that holds events: the key-to-partition mapping changes and order is lost.

## Consumers

```yaml
spring:
  kafka:
    bootstrap-servers: ${SPRING_KAFKA_BOOTSTRAP_SERVERS:localhost:9092}
    consumer:
      group-id: orders-query-service
      auto-offset-reset: earliest
```

```java
@Component
public class OrderEventListener {

    private static final Logger log = LoggerFactory.getLogger(OrderEventListener.class);

    private static final Map<String, Class<? extends OrderEvent>> TYPES = Map.of(
            "OrderCreated", OrderCreated.class,
            "OrderUpdated", OrderUpdated.class,
            "OrderDeleted", OrderDeleted.class);

    private final OrderProjection projection;
    private final JsonMapper jsonMapper;

    public OrderEventListener(OrderProjection projection, JsonMapper jsonMapper) {
        this.projection = projection;
        this.jsonMapper = jsonMapper;
    }

    @KafkaListener(topics = OrderEvent.TOPIC)
    public void on(ConsumerRecord<String, String> record) {
        Header header = record.headers().lastHeader("event-type");
        String type = header == null ? null : new String(header.value(), StandardCharsets.UTF_8);
        Class<? extends OrderEvent> eventClass = type == null ? null : TYPES.get(type);
        if (eventClass == null) {
            log.atWarn().addKeyValue("eventType", type).addKeyValue("offset", record.offset()).log("Unknown event type skipped");
            return;
        }
        projection.apply(jsonMapper.readValue(record.value(), eventClass));
    }
}
```

```java
@Configuration
public class KafkaConsumerConfig {

    /** Three retries one second apart, then the record goes to the dead-letter topic and the listener moves on. */
    @Bean
    DefaultErrorHandler kafkaErrorHandler(KafkaOperations<Object, Object> kafka) {
        return new DefaultErrorHandler(new DeadLetterPublishingRecoverer(kafka), new FixedBackOff(1000L, 3));
    }

    @Bean
    NewTopic orderEventsDeadLetter() {
        return TopicBuilder.name(OrderEvent.TOPIC + "-dlt").partitions(3).replicas(1).build();
    }
}
```

- **Idempotent.** The projection ignores an event that is not newer than the stored version (`cqrs.md`, Projection). Do not add a separate table of processed message ids for a projection.
- **Dead-letter topic with bounded retries.** Spring Boot applies the `DefaultErrorHandler` bean to every listener. A record that still fails after the retries is published to `<topic>-dlt` (the Spring for Apache Kafka 4 default name) on the same partition number, so the dead-letter topic needs at least as many partitions. Without the handler one broken record blocks its partition forever.
- **Unknown event types are skipped** with a warning, so an older query service keeps working when the command service adds an event type.
- **Alert on the dead-letter topic.** A record there means a read model is missing a change until someone fixes the cause and publishes the record again.
- The offset is committed by the listener container after the listener returns. Do not enable auto commit.
- One consumer group per service (`<service-name>`). Replicas of the query service share it.

### Rebuilding a Projection

1. Stop the query service.
2. Empty the read-model tables of the projection.
3. Reset the consumer group to the start of the topic (`kafka-consumer-groups.sh --reset-offsets --to-earliest --execute --group <group> --topic <topic>`), or give the service a new `group-id`.
4. Start the service; it replays every event.

This is how a new read model, or a changed one, is filled. It works only because the topic has no retention limit.

## Local Kafka (Docker Compose)

```yaml
services:
  kafka:
    image: apache/kafka:4.1.0
    ports:
      - "9092:9092"
    environment:
      KAFKA_NODE_ID: 1
      KAFKA_PROCESS_ROLES: broker,controller
      KAFKA_LISTENERS: INTERNAL://:29092,EXTERNAL://:9092,CONTROLLER://:9093
      KAFKA_ADVERTISED_LISTENERS: INTERNAL://kafka:29092,EXTERNAL://localhost:9092
      KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: INTERNAL:PLAINTEXT,EXTERNAL:PLAINTEXT,CONTROLLER:PLAINTEXT
      KAFKA_INTER_BROKER_LISTENER_NAME: INTERNAL
      KAFKA_CONTROLLER_LISTENER_NAMES: CONTROLLER
      KAFKA_CONTROLLER_QUORUM_VOTERS: 1@kafka:9093
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1
      KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR: 1
      KAFKA_TRANSACTION_STATE_LOG_MIN_ISR: 1
    healthcheck:
      test: ["CMD-SHELL", "/opt/kafka/bin/kafka-broker-api-versions.sh --bootstrap-server localhost:9092 > /dev/null 2>&1"]
      interval: 5s
      start_period: 20s
    volumes:
      - kafka:/var/lib/kafka/data
volumes:
  kafka:
```

- Two listeners: an application on the host uses `localhost:9092`, a container in the same Compose project uses `kafka:29092`.
- The healthcheck is `CMD-SHELL` (`spring-boot` skill, `references/cloud.md`), so `docker compose up -d --wait` returns once the broker answers.
- KRaft mode, one node: no ZooKeeper.

## Quick Reference

| Rule | How |
|------|-----|
| No direct publish in a business transaction | `Outbox.append` in the handler, `OutboxRelay` publishes |
| Key | Aggregate id |
| Topic | One per aggregate type, `<aggregate>-events`, `retention.ms=-1` |
| Producer | `acks: all`, `enable.idempotence: true` |
| Consumer | `@KafkaListener` → projection with a version check |
| Failures | `DefaultErrorHandler` + `DeadLetterPublishingRecoverer`, `<topic>-dlt` |
| Local | `apache/kafka` in Docker Compose with a healthcheck |
| Tests | Testcontainers `KafkaContainer` with `@ServiceConnection` (`testing.md`) |
